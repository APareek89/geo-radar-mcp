## 2026-07-16 — Auth0 public-signup path: full E2E PROVEN (and the complete gotcha list)
**What happened:** After the WorkOS→Auth0 switch, the claude.ai connector connected but tool calls failed. Final root cause was OURS: Auth0's `iss` claim is `https://tenant.us.auth0.com/` **with a trailing slash**, and `verifyAccessToken` compared against the normalized no-slash `OAUTH_ISSUER` → every valid token 401'd. Fixed by accepting both forms for `iss` (commit 3a10cb3), like the earlier `aud` fix. **Proof:** minted a real Auth0 JWT (client_credentials via the API's auto-created Test Application + a client-grant) and hit live `/mcp`: initialize 200 + all 8 tools listed.
**The complete Auth0-DCR gotcha sequence (each was a distinct error):** (1) `Service not found: <resource>` → the `resource` param must EXACTLY match an API Identifier — create the API with the **trailing slash** (`https://geo-radar-mcp.onrender.com/`); (2) `Client is not authorized to access resource server` → API Settings → **Default Permissions for third-party applications = All** (+ Application Access Policy → all applications) — DCR clients are third-party and can't be granted per-app; (3) `403 too_many_entities` on register → the trial tenant's app limit; every failed Connect + probe creates a `tpc_` app — delete old ones (Applications list); (4) `no connections enabled for the client` → third-party clients only see **domain-level** connections; dashboard "Enable Application Connections" does NOT cover this — needs Management API `PATCH /api/v2/connections/{id} {"is_domain_connection": true}`; (5) our issuer trailing-slash bug (above).
**Watch for later:** any IdP swap → check BOTH `iss` and `aud` slash conventions against the live token, not the docs. `read -s -p` is bash-only (hangs in zsh — user's shell). Long secrets get corrupted when retyped inline in Bash; Write them to a file instead. Auth0 Management API tokens from API Explorer expire in 24h.

## 2026-07-16 — FREE OAuth: self-host the AS (no WorkOS) — `OAUTH_MODE=selfhosted`
**What happened:** WorkOS charges for production and staging is too slow (504s). Since the fix for the web-connector `state` bug is just "be a same-origin AS," we don't need WorkOS at all — built a self-hosted AS that issues its own tokens.
**How:** `apps/mcp-server/src/self-oauth.ts` implements the MCP SDK's `OAuthServerProvider`: in-memory clients (DCR mints `client_id`) + one-time auth codes; `mcpAuthRouter` serves metadata + `/authorize|/token|/register` on our origin. `/authorize` is gated by `selfHostedLoginGate` (HTTP Basic vs `MCP_LOGIN_PASSWORD` — browser shows a native dialog, no custom form). Tokens are HS256 JWTs signed with `OAUTH_SIGNING_SECRET` (falls back to `MCP_API_KEY`); `verifySelfIssuedToken` checks them and `auth.ts` `requireAuth` uses it when `OAUTH_MODE=selfhosted`. The SDK's token handler does PKCE for us (we just store/return the `code_challenge` via `challengeForAuthorizationCode`). Env to go live: `OAUTH_MODE=selfhosted` + `OAUTH_AUDIENCE`(=issuer, no slash) + `MCP_LOGIN_PASSWORD` + `OAUTH_SIGNING_SECRET`.
**Gotchas:** (1) `authConfigured()` must return true for `selfhosted` (else `/mcp` would be open since `OAUTH_ISSUER` is unset). (2) `OAUTH_SIGNING_SECRET` must be STABLE — a restart with an ephemeral key invalidates all issued tokens. (3) No refresh tokens issued — Claude re-runs the (fast, same-origin) flow on expiry (default TTL 7d). **Watch for later:** clients + codes are per-instance in-memory; if the web dyno scales >1 or restarts mid-flow, Claude re-registers/re-auths (fine for single dyno). Move to Postgres if multi-instance.

## 2026-07-16 — ioredis "Unhandled error event" spam when Redis is down
**What happened:** Booting locally with `REDIS_URL` in `.env` but no Redis running spammed `[ioredis] Unhandled error event: ECONNREFUSED`. **Root cause:** `RedisTokenBucketLimiter` created the connection with no `error` listener. **Fix:** attach `redis.on("error", …)` that logs once (acquire() already fails open, so an outage never blocks work). **Watch for later:** any new ioredis/bullmq connection needs an `error` handler or Node logs unhandled-error noise.

## 2026-07-16 — Fire-and-forget queue: "queued" response vs "running" DB row
**What happened:** Made `QueuePanelRunner` fire-and-forget — it now returns `{status:"queued", report_id}` immediately and a worker finishes the run. To return a `report_id` before the worker starts, the WEB tier pre-creates the run row (`beginRun`) and passes `{runId, brandId}` in the job; the worker calls `runner.run(input, existingRun)` which skips `beginRun` and finishes THAT row.
**Gotcha:** `store.beginRun()` sets status **`running`** (both Memory + Drizzle), not `queued`. So the `measure_share_of_voice` *response* says `status:"queued"` but `get_report(report_id)` shows `running` until the worker completes it. Both are non-terminal — the client polls until `completed`/`failed`. Don't "fix" this by asserting `queued` in tests; assert `!== "completed"`. Changing beginRun to write `queued` would need a store-API/status change (out of scope).
**Watch for later:** the job payload changed from bare `input` to `{input, runId, brandId}` — any code reading `job.data` must use `job.data.input`. `QueuePanelRunner` now needs the `store` (constructor arg) — `new QueuePanelRunner(REDIS_URL, store)`.

## 2026-07-16 — After the proxy fix, Connect 504s — WorkOS *staging* is too slow (not Render)
**What happened:** With `OAUTH_MODE=proxy`, the flow got all the way to `…authkit.app/api/callback?code=…&state=…` (so the `state` bug is SOLVED — code + state round-tripped), then failed with a **Cloudflare 504 Gateway time-out** whose failing Host was `qualified-odyssey-45-staging.authkit.app` (Render is not in this hop). Probed WorkOS staging directly: `/oauth2/authorize` took **4–50s** per call, one returned **504 at 60s**, and even `/oauth2/jwks` (13s) and AS metadata (29s) were pathologically slow. Earlier in the session staging also gave a transient 504 on `/oauth2/register`.

**Fix:** Use a WorkOS **production** AuthKit environment (point `OAUTH_ISSUER` at the prod domain; re-enable DCR+CIMD + the Resource Indicator there). Warm retries on staging occasionally pass but stay flaky. **Watch for later:** any 504 mid-OAuth with Host = `*.authkit.app` = WorkOS env slowness, not our stack — check the Cloudflare diagram's Host box before touching Render/our server.

## 2026-07-16 — Fix for the web-connector `state` bug: be our own AS (OAuth proxy)
**What happened:** Built `OAUTH_MODE=proxy` — this server becomes the same-origin OAuth authorization server Claude talks to, forwarding `/authorize|/token|/register` to WorkOS. Mirrors `mcp.pixelbin.io`'s working topology (advertises itself as its own `authorization_server`), sidestepping the cross-origin `state` drop.
**How (small, mostly SDK wiring):** MCP SDK v1.29 ships `ProxyOAuthServerProvider` + `mcpAuthRouter` (import from `@modelcontextprotocol/sdk/server/auth/providers/proxyProvider.js` and `.../server/auth/router.js`). New `oauth-proxy.ts`: subclass the proxy provider to **cache clients on the proxied `/register`** — WorkOS has no "GET client" endpoint but the SDK's authorize handler calls `getClient(id)` to validate `redirect_uri`, so without the cache authorize fails. `mcpAuthRouter` serves BOTH well-known metadata docs (issuer/resource = our own URL). `auth.ts` gained `verifyAccessToken→AuthInfo` (reused by `/mcp` + the provider).
**Gotcha — express-rate-limit vs `trust proxy: true`:** the SDK rate-limits `/authorize|/token|/register`; with `app.set("trust proxy", true)` (permissive) express-rate-limit throws `ERR_ERL_PERMISSIVE_TRUST_PROXY` (logged per request, rate-limiting silently ineffective). Fix: `trust proxy` = **`1`** (Render = single reverse proxy) — satisfies the limiter AND still yields https from X-Forwarded-Proto (verified: WWW-Authenticate stays `https://`).
**Watch for later:** the client cache is per-instance in-memory — on a web-dyno restart a client is re-registered by Claude on its next attempt (fine for 1 dyno). If Render scales the web service >1 instance, move the cache to Postgres or clients won't resolve across instances.

## 2026-07-16 — `state: Field required` is a claude.ai-web-connector bug, NOT our server (proven by probe)
**What happened:** After shipping the metadata fixes AND the user confirming WorkOS is fully configured (Resource Indicator `https://geo-radar-mcp.onrender.com` no-slash, DCR + CIMD both Enabled), the claude.ai connector STILL failed with `{"invalid_request_error","message":"state: Field required"}` + an `ofid_...` (Claude's OAuth-orchestrator failure id).
**Root cause (proven):** Probed WorkOS directly with curl — DCR `/oauth2/register` returns a client_id (one transient 504 = staging cold-start, retry succeeds); `/oauth2/authorize` with `state=probe_state_ABC123` returns `302` and the redirect **preserves `state` exactly** (`Location: .../?authorization_session_id=…&state=probe_state_ABC123`), with AND without the `resource` param. So WorkOS accepts the request and round-trips state correctly. The missing `state` therefore originates in **Claude's own MCP OAuth orchestrator** (Anthropic `req_`/`ofid` ids) in the *external-authorization-server delegation* path — a known family of bugs (claude-ai-mcp #122/#212, claude-code #17733). Per #212 the failure is **specific to the claude.ai web / Desktop connector**; the **Claude Code CLI path (`claude mcp add --transport http`) works** against the same server.
**Fix / workaround:** Not fixable in our server or WorkOS config. Unblock options: (1) connect via **Claude Code CLI** (proves the server E2E); (2) try the **manual OAuth Client ID** path in the web connector; (3) robust long-term: make our MCP server the OAuth **authorization server / proxy** so Claude uses its standard (working) DCR-against-the-MCP-server flow instead of the buggy external-AS indirection.
**Decisive comparison (why another MCP connects but ours doesn't):** `mcp.pixelbin.io` connects fine in the SAME claude.ai web connector. Curl shows why — it advertises `authorization_servers: ["https://mcp.pixelbin.io"]` (itself) and hosts its OWN `/.well-known/oauth-authorization-server` with `/oauth/authorize|token|register` on its own domain. So Claude runs the standard **DCR-against-the-MCP-server** flow (one origin = the working path). Ours advertises `authorization_servers: [WorkOS]` (a different origin) and hosts no AS metadata → Claude runs the **cross-origin delegation** flow, which is where its web connector drops `state`. **So the robust fix = be our own AS** (host `/oauth/authorize|token|register` + AS metadata pointing to ourselves; proxy/wrap WorkOS underneath, or self-issue). pixelbin is the working reference shape.
**Watch for later:** If a future Claude web-connector update round-trips state across origins, delegation will "just start working." Don't chase server-side causes for `state: Field required` when a curl probe shows the upstream AS preserving state.

## 2026-07-16 — Remote "Connect & log in" fails with `state: Field required` (OAuth metadata non-conformance)
**What happened:** Adding the Render URL as a custom connector in Claude and clicking Connect failed during the authorize/callback with `{"type":"invalid_request_error","message":"state: Field required"}` (an Anthropic `req_` id — so Claude's own OAuth proxy rejected the callback, before the token exchange ever reached WorkOS or us).
**Root cause (server side, what we could fix):** Our RFC 9728 protected-resource metadata was non-conformant for WorkOS AuthKit in two ways: (1) it advertised `scopes_supported: ["mcp"]`, but WorkOS AuthKit only grants `openid/profile/email/offline_access` — advertising a scope the authorization server can't grant is a documented trigger for the `code/state: Field required` callback-validation failure (a whole family of GitHub issues: anthropics/claude-ai-mcp #122/#212, claude-code #17733); (2) `OAUTH_AUDIENCE` had a **trailing slash**, so the advertised `resource` was `https://geo-radar-mcp.onrender.com/` — this becomes the `resource` indicator Claude sends to WorkOS and the `aud` we later require, and it must match the resource indicator registered in WorkOS **byte-for-byte** (a trailing-slash mismatch surfaces later as an `aud`-mismatch "invalid token" at `/mcp`).
**Fix:** `auth.ts` — dropped `scopes_supported` entirely (matches WorkOS's documented AuthKit-MCP metadata shape; clients read grantable scopes from the AS metadata anyway); added `audienceUrl()` that strips a trailing slash from `OAUTH_AUDIENCE` for BOTH the advertised `resource` and the `aud` verification; added `realm="MCP"` to the 401 `WWW-Authenticate` (matches known-working community configs). Added `auth.test.ts` (3 tests) pinning the shape.
**Watch for later:** The *definitive* root cause of a `state: Field required` needs the **WorkOS dashboard event log** for the authorize request Claude sent — check whether `state` and `scope` are present and whether the `resource` param matches a registered Resource Indicator. Anthropic-side variant (#17733): Claude omits `state` on authorize but validates it on callback — not fixable by us; use the Plan-B manual OAuth Client ID path. USER must also set Render `OAUTH_AUDIENCE` = `https://geo-radar-mcp.onrender.com` (no slash) and register that exact string as the WorkOS Resource Indicator.

## 2026-07-16 — pnpm 11 refuses ignored build scripts (turbo install check fails)
**What happened:** After adding bullmq + @google-analytics/data, `pnpm install` exited 1 with `ERR_PNPM_IGNORED_BUILDS` (msgpackr-extract, protobufjs), which made `turbo run` fail its dependency-status check before any task ran.
**Root cause:** pnpm 11 won't silently skip dependency build scripts; a linter had written placeholder values (`set this to true or false`) into `allowBuilds:` in pnpm-workspace.yaml, which are invalid.
**Fix:** Set `allowBuilds: { msgpackr-extract: false, protobufjs: false }` (they're optional native accelerators with pure-JS fallbacks — no need to compile). `pnpm install` then exits 0 and turbo runs.
**Watch for later:** Any new dep with a postinstall/native build will trip this — add it to `allowBuilds` (true to compile, false to skip) in pnpm-workspace.yaml.

## 2026-07-16 — Wiring the app to GCP Cloud SQL (gotchas)
**What happened:** Connected the server to a real GCP Cloud SQL Postgres and ran the full pipeline live.
**Gotchas / root causes:**
- `gcloud components install cloud-sql-proxy` reports success but the v2 binary isn't on PATH; it lives at `/opt/homebrew/share/google-cloud-sdk/bin/cloud-sql-proxy`. Call it by full path.
- The proxy authenticated cleanly with `--token="$(gcloud auth print-access-token)"` (avoids relying on ADC being the right identity).

**Watch for later:** If `pnpm start:mcp` errors connecting to `localhost:5432`, the GCP instance is Stopped or the proxy isn't running — start both, or use `GEO_STORE=memory` for offline dev.
